# 部署总览与 H100 → H20 兼容性分析

> 项目：车网互动充电功率预测 — 7 模型统一 benchmark（voltaic/）
> 编写日期：2026-08-24
> 目标：把本机（H100）上验证过的 Python 程序，离线迁移到北京离线 H20 机房运行。

---

## 一、结论先行（TL;DR）

**H100 上的方案可以直接在 H20 上使用，风险极低，几乎零改动。** 原因有三：

1. **硬件/系统层完全对齐**：H100 与 H20 都是 x86_64 + NVIDIA GPU，操作系统都是 Ubuntu 22.04.5 LTS，GPU 驱动都是 575.57.08，CUDA 都是 12.9（详见 §三环境对比表）。
2. **本项目的计算负载是 CPU 级的，GPU 差异无关紧要**：28 个 case、每个 case 仅 2000~4000 行数据，7 个模型里 3 个是纯统计/树模型（纯 CPU），3 个深度学习模型（PatchTST d_model=64 / TimesNet d_model=32 / GRU hidden=32）都是玩具级规模，全流程在 CPU 上几分钟内跑完。
3. **依赖清单本来就是 CPU-only**：`code/requirements.txt` + `torch` CPU 版，**根本不调用 CUDA**，所以 H100/H20 之间 GPU 代数差异、显存差异、算力差异对这个任务**没有任何影响**。

唯一必须修的两处代码问题（均已修复，见 §五）：

| 问题 | 位置 | 处理 |
|------|------|------|
| 硬编码了 macOS 路径 `/Users/arthas/git/photovoltaic/...` | `code/run_merged_benchmark.py` | 已改为相对脚本位置的自适应路径 |
| Dockerfile 入口指向不存在的 `scripts/run_experiment_v2.py` | `code/Dockerfile` | 已改为 `run_merged_benchmark.py` |

## 二、两个部署方案怎么选

| 维度 | 方案一：离线 Python 环境 | 方案二：Docker 镜像 |
|------|------------------------|---------------------|
| 交付物 | 代码 + 数据 + `wheels/`（268MB） | 单个 `excharge-pred.tar.gz`（约 500MB） |
| 目标机依赖 | 需有 Python 3.11 + pip | 只需 Docker（H20 已装 29.1.3） |
| 联网要求 | 目标机完全离线可用 | 目标机完全离线可用 |
| 环境隔离 | 依赖目标机 Python 环境干净 | 完全隔离，最稳 |
| 推荐场景 | 想直接在宿主机 Python 里跑、便于调试 | 生产/评测环境、要一致复现 |

**建议**：既然目标 H20 已预装 Docker 29.1.3，且你在 H20 上要"执行一次镜像包"，**优先走方案二（Docker）**，一次打包、处处一致；方案一作为不依赖 Docker 的兜底。

两个方案都要在**本机（H100，有网）**准备好"离线包"，再拷到 H20（离线）执行。步骤见各自文档。

## 四、为什么"CPU-only"是对的选择

本项目 `code/requirements.txt` 明确走 CPU 路线，这带来三个直接好处：

1. **跨卡零风险**：CPU 版 torch 不链接任何 CUDA/驱动，H100/H20/昇腾(CPU 回退) 都能跑，不存在"驱动/CUDA 版本不匹配"的经典坑。
2. **离线包小**：CUDA 版 torch wheel 约 2.5GB，CPU 版约 200MB。离线拷贝成本低一个数量级。
3. **负载根本不配 GPU**：数据 17MB、模型几万个参数，GPU 启动开销都远超计算本身。

结论：**不要**为了"H20 有 8 张 GPU"而把 torch 换成 CUDA 版——那是给自己挖离线迁移的坑。等未来真要跑大规模训练/推理再单独评估 CUDA 版。

## 六、昇腾 910C（NPU）注意事项（备用）

项目文档里还有第二台服务器"昇腾 910C"（aarch64 + Ascend NPU + openEuler + CANN 8.5.0）。如果未来也要上昇腾：

- **CPU 回退可直接跑**：代码里 `torch.device("cuda" if torch.cuda.is_available() else "cpu")` 在昇腾上 `cuda.is_available()` 为 False，自动回退 CPU，模型仍能跑（纯 CPU 逻辑），只是不用 NPU。
- **要用 NPU 需改造**：需要 `torch_npu` + CANN，且代码里所有 `torch.cuda`/`.cuda()` 调用要换成 `torch_npu`，这是额外工作，目前不需要。
- **架构不同**：离线 wheel 需下载 aarch64（manylinux_aarch64）版本，与 x86_64 的 `wheels/` 不通用。

本次交付聚焦 H20（x86_64），昇腾路线仅记录在此备忘。

## 七、本机验证结果

在本机（H100）已用 Python 3.11.15 venv 完整跑通 `run_merged_benchmark.py`（28 case，7 模型，退出码 0），结果写入 `predictions/merged_benchmark.json`。

- **确定性模型（All-Zero / Slot-Median / LightGBM / DEMMFL）与项目 README 逐位一致**：MAE 分别为 31.54 / 27.68 / 31.69 / 29.47，F1 0.000 / 0.662 / 0.696 / 0.715。
- **深度学习模型（GRU / PatchTST / TimesNet）首次运行与 README 有 ±0.5 的波动**（GRU 29.55 vs 30.04、PatchTST 34.25 vs 33.74、TimesNet 36.37 vs 37.08），原因是原代码未设随机种子；已加 seed=42 修复（见 §五第 3 条），后续可复现。

这证明修复后的代码在 x86_64 + Ubuntu 22.04 + Python 3.11 上可复现，与 H20 环境同构。
